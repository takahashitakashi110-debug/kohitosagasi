対象: Codex CLI（実装担当）
作業場所: この依頼書が入っているブランチ `codex/e2e-buttons` と、そのドラフト PR（Issue に番号を記載）
前提: `AGENTS.md` と `docs/WORKFLOW.md`（v0.4 以降）に従うこと。**新しいブランチや PR は作らない**。

> **着手の条件**: この依頼は PR #16（依頼 F: 音とミュートボタン、ボタン配置テスト `tests/button-layout.test.ts`）を前提にする。
> 着手前に PR #16 が本流に入っていることを確認し、`git fetch origin` と `git merge origin/<本流>` で取り込んでから始めること。
> PR #16 がまだ本流に入っていなければ、着手せずに PR にその旨をコメントして待つこと。

## 0. 目的

PR #16 のレビューで、「散策画面のミュートボタンがアルバムボタンに 6px 重なり、アルバムの下端を押すとミュートが切り替わる」不具合が見つかった。
これは**実ブラウザで実際に押して**初めて見つかった種類の不具合で、単体テスト・Codex の自動レビューでは検出されなかった。
PR #16 で追加された配置テスト（ボタンの矩形が重ならないこと）は再発を防ぐが、「押したら本当にその機能が動く」ことまでは確かめていない。

この依頼で、PR #16 のレビューで手作業で行った確認を、**GitHub の CI で毎回、実ブラウザ（スマホ幅）で自動的に繰り返す**。

## 1. 合格条件（この3つを満たすこと）

1. **スマホ幅の散策画面でアルバムボタンの下端をタップすると、アルバムが開き、ミュート設定が変わらない。**
2. **ミュートボタンをタップすると、ミュートだけが切り替わる。**
3. **GitHub の CI でこの操作を再現し、成功時は確認画像、失敗時は画像と操作記録を保存する。PR の報告からその結果を開ける。**

## 2. 変更してよいファイル

- `package.json` / `package-lock.json` … `@playwright/test` を **devDependencies に追加**（MVP 指示書 §0「devDependencies は typescript / vite / vitest のみ」の例外として、この依頼で許可する）。
  バージョンは `^` / `~` を付けず**固定**する。実行時依存（`dependencies`）は空のまま。`e2e` などの npm スクリプトの追加は可。
- `playwright.config.ts`（新規）、`e2e/`（新規フォルダ。実ブラウザのテスト）
- `.github/workflows/ci.yml` … 既存の `test` ジョブは**変えずに**、実ブラウザ用のジョブを**追加**する
- `tsconfig.json` … `include` に `e2e` と `playwright.config.ts` を足す程度
- `src/main.ts` … §4 の**読み取り専用**の確認用フックの追加のみ
- `tests/` … PR #16 の配置テストの判定処理を共通化する変更（**判定の内容・期待値は変えない**）、テストの追加
- `.gitignore` … Playwright の出力先（`test-results/`、`playwright-report/` など）の追加
- `docs/HANDOVER.md` … 対応済みの記録と、実ブラウザテストの動かし方

**変えてはいけないもの**: ゲームのルール・採点・セーブ（`src/game/`）、ボタンの位置や見た目、既存のテストの期待値、既存の `test` ジョブ。

## 3. 実ブラウザテストの中身（`e2e/`）

### 3-1. 環境

- Playwright の Chromium。**スマホ幅** `390×844`、`hasTouch: true`、`isMobile: true`、`deviceScaleFactor: 2`。
  可能なら `360×640` でも同じテストを回す（Playwright の `projects` で2つ）。
- アプリは `npm run build` の成果物を `vite preview` で配信して開く（`playwright.config.ts` の `webServer` を使ってよい）。
- **タップは `page.touchscreen.tap()` で行う**（マウスのクリックではなく、スマホの指に近い操作で確かめる）。
- 各テストの最初に `localStorage` を空にして、新しいゲームとして始める。

### 3-2. 散策画面までの進め方

タイトル →「はじめる」→ 地図 → どれか1つのスポット、を**実際のタップで**進める（ボタンの位置は §4 のフックから読み取る。座標の決め打ちはしない）。

### 3-3. テスト

**テスト① アルバムボタンの下端**
1. 散策画面で、§4 のフックから今描かれている**ボタンの矩形**を読み取る。
2. まず、PR #16 の配置テストと**同じ判定**で、実画面のボタンどうしが重なっていないことを確かめる（§5）。
3. アルバムボタンの矩形の**下端から 2 論理px 内側、左右中央**を、画面上の座標に換算してタップする（換算はキャンバスの実際の表示位置と大きさから行う）。
4. **アルバムが開いた**（場面が `album`）ことを確かめる。
5. **ミュート設定が変わっていない**（`localStorage` の `kohitosagasi.settings.v1` がタップ前と同じ。初回なら未保存のまま）ことを確かめる。
6. 確認画像を保存する。

**テスト② ミュートボタン**
1. 散策画面で、ミュートボタンの矩形の中央をタップする。
2. ミュートが切り替わった（`kohitosagasi.settings.v1` の `muted` が `true`）ことを確かめる。
3. **ミュート以外は変わっていない**ことを確かめる: 場面は `field` のまま、セーブデータ（`kohitosagasi.save.v1`）はタップ前と同じ、アルバムは開いていない。
4. もう一度タップして `false` に戻ることを確かめる。
5. 確認画像を保存する。

## 4. 確認用フック（`src/main.ts`）

キャンバスのゲームは画面の中身を DOM から読めないため、**読み取り専用**のフックを1つだけ足す。

- URL に `?e2e=1` が付いているときだけ、`window.__kohitoE2E` を公開する。中身は次の**読み取り専用**の関数だけ。
  - `scene(): string` … 今の場面
  - `buttons(): { x, y, w, h, action }[]` … 直近の描画で記録されたボタンの矩形（`ui.buttons` の**写し**）
- ゲームの状態を書き換える関数は**作らない**。操作はすべて実際のタップ・キー入力で行う。
- `?e2e=1` が無いときは何も公開しない（通常のプレイに影響しない）。このことを単体テストで確かめる。

## 5. PR #16 の配置テストを活かす

- `tests/button-layout.test.ts` の「2つの矩形が重なるか」の判定（辺が触れても不合格）を、共通の関数として切り出す（例: `tests/support/buttons.ts`）。
- 単体テスト（`tests/button-layout.test.ts`）と実ブラウザテスト（`e2e/`）の**両方が同じ関数を使う**。
  単体テストの判定内容と期待値は変えない（切り出しのみ）。
- これで「描画の上では重ならない（単体）」と「実画面でも重ならず、押した機能が動く（実ブラウザ）」を同じ基準で守る。

## 6. CI（`.github/workflows/ci.yml`）

- 既存の `test` ジョブは変えない。実ブラウザ用のジョブ（例: `e2e`）を**追加**する（`push` と `pull_request` の両方で動く）。
- ブラウザの用意は `npx playwright install --with-deps chromium` 等で行う。
- **結果の保存（アーティファクト）**:
  - **成功時**: 確認画像（テスト①②の画像）を保存する。
  - **失敗時**: 画像と**操作記録**（Playwright のトレース `trace.zip`。可能ならスクリーンショットも）を保存する。
  - Playwright の設定は、トレースを**失敗時だけ**残す（`retain-on-failure` 等）。成功時に全テストのトレースを録らない（CI が重くなるため）。
  - 保存期間は 14 日程度。
- **PR から結果を開けるようにする**:
  - ジョブの最後に、実行結果の要約（テストの合否と、アーティファクトの名前）を **ジョブの要約**（`$GITHUB_STEP_SUMMARY`）に書く。
  - 完了報告（§8）に、その **CI の実行ページと、アーティファクトへのリンク**を載せる。
- 使う GitHub Actions の部品（アーティファクトの保存など）のバージョンは、**採用する時点で公式のリリースページで最新を確認して固定**し、その確認元を報告に書く。

## 7. 失敗時の保存を、実際に確かめる

合格条件③の「失敗時は画像と操作記録を保存する」を確かめるため、**一度だけ、わざと失敗させた CI を走らせる**。

1. ミュートボタンを PR #16 の修正前の位置（アルバムに重なる位置）に戻す**一時的な commit** を push する。
2. 実ブラウザのジョブが**失敗し**、画像と `trace.zip` がアーティファクトに残ることを確かめる。
3. その一時的な変更を**打ち消す commit** を push して元に戻す（履歴の書き換え・force push はしない）。
4. 失敗した実行と成功した実行の両方のリンクを、完了報告に載せる。

（ローカルでも同じ一時的な変更でテストが落ちることを先に確かめてから行うこと）

## 8. 受け入れ条件

1. `npm run typecheck` / `npm test` / `npm run build` が通る（既存の件数＋追加分。既存の期待値は不変）。
2. 手元で実ブラウザテスト（例: `npm run e2e`）が通る。
3. PR の CI で、既存の `test` ジョブと新しい実ブラウザのジョブがどちらも ✅。成功時の確認画像がアーティファクトに残っている。
4. §7 の失敗の実行で、画像と操作記録がアーティファクトに残っている。
5. 完了報告（WORKFLOW.md §6 の形式）に、成功した実行・失敗した実行・各アーティファクトへのリンクがあり、PR から開ける。
6. §2 のファイル以外を変更していない。`dependencies` は空のまま。

## 9. 進め方（WORKFLOW.md v0.4）

1. PR #16 が本流に入っていることを確認する（入っていなければ PR にコメントして待つ）。
2. `git fetch origin` のあと、このブランチ `codex/e2e-buttons` を専用の作業フォルダに取り出し、本流を取り込む。
3. 着手したら一度 push する。
4. 実装・検査・CI ✅（§7 の失敗の確認を含む）のあと、WORKFLOW.md §6 の形式で**この PR にコメント**し、Ready for review にする。
5. merge はしない。
