# GitHub 上の作業の進め方 v0.4（試行版）

このリポジトリで作業する**すべての人と AI（Codex / Claude）**が従うルールです。
作業を始める前に必ず読んでください。ルールを変えたいときは、このファイルを変更する PR を出して合意を取ります。

> 試行中の注意: 本流ブランチは現在 `claude/confident-gauss-tbl22i` です（将来 `main` に改名予定）。
> このファイルで「本流」と書いたら、このブランチのことです。

---

## 1. 役割

| 役割 | 誰 | やること | やらないこと |
|---|---|---|---|
| 持ち主 | リポジトリの所有者 | 依頼の判断、PR の **merge**、ルールの最終決定 | — |
| 実装担当 | 参加者と各自の Codex | 依頼書どおりに実装し、テストを書き、PR で提出する | merge、main への直接 push |
| 検査担当 | Claude | 依頼書の作成、PR のレビュー（差分・テストの効き・見た目）、進み具合の把握 | merge、依頼の範囲外の実装 |
| 自動検査 | CI（`.github/workflows/ci.yml`） | push / PR のたびに型チェック・テスト・ビルドを実行 | 判断はしない（合否だけ） |

## 2. アカウント

- **1人1アカウント**。アカウントを複数人で共有しない。
- 各自の Codex は、**その人自身の GitHub アカウント**で接続する。
- Claude の GitHub への書き込みは、持ち主のアカウント名義で行われる（コメント末尾に「Generated by Claude Code」が付く）。

## 2-2. 作業フォルダ

- **1つの AI（または1人）に1つの作業フォルダ**。同じフォルダを複数の AI で共有しない。
  共有すると、誰かがブランチを切り替えた瞬間に、他の AI が見ているファイルが入れ替わる・消える。
- 同じ PC で複数の AI を動かすときは、`git worktree` でブランチごとに別のフォルダを作る。
  ```
  git fetch origin
  git worktree add ../kohitosagasi-<名前> <ブランチ名>
  ```
  新しいフォルダでは最初に `npm install`（または `npm ci`）を実行する。
  使い終わったら `git worktree remove ../kohitosagasi-<名前>` で片付ける。

## 3. 依頼の出し方（Issue）

- 1つの依頼 = 1つの Issue。タイトルは `<記号>: <内容>`（例 `A: こひとの仮絵の描き分け`）。
- 詳しい仕様は `docs/REQUEST_<記号>_*.md` に置き、Issue からリンクする。Issue に全文を貼ってもよいが、**食い違ったらファイル側が正**。
- 依頼書には必ず次を書く: 目的 / 変更してよいファイル / 変えてはいけないもの / テストの条件 / 受け入れ条件。

### 3-2. 作業用ブランチと PR は、依頼を出す側（Claude）が先に作る

PR 番号を人づてに受け渡すと途切れやすい（試行の依頼 B で発生）。そのため、依頼を出すときに Claude が次をまとめて行う。

1. 本流の最新から作業用ブランチ `codex/<短い英語名>` を作り、依頼書 `docs/REQUEST_*.md` を commit して push する
   （ブランチ名と依頼書には Issue 番号を書かない。番号はまだ決まっていないため）。
2. そのブランチから本流へ**ドラフト PR** を作る。Claude はすぐ監視を始める。
3. **最後に Issue を、全文入りで一度に作る**（依頼書の全文と「作業場所: ブランチ `codex/…` / PR #…」）。
   仮の本文で作ってあとから書き換えてはいけない（実装担当の自動監視が、作成時の本文しか読まない場合がある。依頼 C で発生）。
4. PR の説明の1行目に `closes #<Issue番号>` を書き足す。

これで、実装担当の最初の push から検査担当に自動で届く。依頼書は実装と同じ PR で本流に入る（依頼書だけの PR は作らない）。
補助として、依頼が出ている間、Claude は 20 分ごとに「依頼の Issue を参照する別の PR」が無いかを探す。

## 4. 作業の流れ（実装担当）

1. **Issue に書かれた作業用ブランチを使う**（§3-2。**自分で新しいブランチや PR を作らない**）。専用の作業フォルダに取り出す:
   ```
   git fetch origin
   git worktree add ../kohitosagasi-<Issue番号> codex/<Issue番号>-<名前>
   ```
   作業場所が Issue に書かれていないときだけ、本流の最新から `codex/<Issue番号>-<短い英語名>` を作り、すぐドラフト PR を出して、
   **Issue にも「PR #… を作成」とコメントする**。Claude が自分の作業をするときは `claude/<内容>`。
   - **作業を再開するとき・push する前**は、本流の最新を取り込む（履歴を書き換えない `merge` を使い、`rebase` はしない）。
     ```
     git fetch origin
     git merge origin/<本流>
     ```
   - 作業ブランチにまだルール文書が無いときは、本流から直接読む:
     `git show origin/<本流>:docs/WORKFLOW.md`
2. **着手したら一度 push する**（着手の記録だけの小さな commit でよい）。検査担当に「着手した」ことが自動で届く。
3. **小さく commit して push する**: 機能ごとに commit を分ける。メッセージは日本語でよい。
4. **自分で検査する**: push の前に必ず手元で実行する。
   ```
   npm run typecheck
   npm test
   npm run build
   ```
5. **CI が ✅ になったことを確認する**。❌ なら原因を直してから次へ進む。
6. **報告して Ready for review にする**: §6 の形式で **PR にコメント**してから、ドラフトを解除する。
7. merge はしない（持ち主が行う）。

## 5. テストの決まり

- **新しい機能・修正には、テストを必ず付ける。**
- **テストを消す・期待値を変える**ときは、PR の説明に「何を・なぜ」を書く。できれば commit も分ける。
- **テストを通すためにテストを弱めない。** 実装が間違っているなら実装を直す。
- 次の**重要なテスト**は、変える前に Issue か PR で持ち主の了承を取る。

  | ファイル | 守っているもの |
  |---|---|
  | `tests/deduction.test.ts` | ヒント5つで推理が成り立つ（どの4つでも絞りきれない） |
  | `tests/playthrough.test.ts` | 3日間でクリアまで遊べる／隠れた尻だけでは全身にならない／逃走記録の保存 |
  | `tests/camera.test.ts` | どの方向から構えても全身が撮れる |
  | `tests/art.test.ts` | 絵が採点の範囲からはみ出さない |
  | `tests/save.test.ts` | 壊れたセーブでも落ちない |

- テストを skip・無効化して CI を通すことは禁止。

## 6. 報告の書き方（PR のコメント）

```markdown
### 結果
完了 / 要確認（理由）

### 対象
closes #<Issue番号> / 依頼書: docs/REQUEST_*.md

### 変更したファイル
- path/to/file … 何をしたか

### 実行結果（実際に実行した出力を貼る）
npm run typecheck … 終了コード
npm test … Test Files / Tests の行
npm run build … built の行

### テストの増減
追加: … / 変更・削除: …（理由）

### 未達・妥協したこと
なし / …

### 検査担当に見てほしいこと
…
```

**自己申告だけで「完了」にしない。** 実行していないものは「未実行」と書く。

## 7. 禁止事項

- 本流への直接 push（PR を通さない変更）
- 履歴の書き換え（rebase・amend・force push）を、他人のブランチや本流で行うこと
- 自分の PR を自分で merge すること（merge は持ち主が行う）
- 依頼書の「変更してよいファイル」以外を変えること（必要なら PR のコメントで相談する）
- 秘密情報（API キー・パスワード）を commit すること
- 実在の地名・店名、既存作品に似せた名前や絵を入れること（`docs/HANDOVER.md` §4 の差別化方針）

## 8. レビューへの対応

- 指摘には、その PR のコメント（または該当のスレッド）で返信する。
- 修正は**同じブランチに追加の commit** で出す（新しい PR は作らない）。
- 「任意」「nit」と書かれた指摘は、対応しなくてもよい。対応しない場合はその旨を返信する。
- 範囲を超える提案（設計の変更など）は、実装せずに PR のコメントで提案する。

## 9. merge まで

1. CI ✅
2. Claude のレビューで「合格」の報告
3. 持ち主が merge
4. 実装担当は、必要なら `docs/HANDOVER.md` を更新する（同じ PR に含める）

## 10. 引き継ぎ

- 作業を終える・中断するときは `docs/HANDOVER.md` を更新する。
- 判断の理由は、会話ではなく**リポジトリの文書に残す**（次の担当者や次の AI セッションは、会話の記憶を持たない）。

## 付録: Codex のスキル

リポジトリ用のスキルが `.agents/skills/kohitosagasi-workflow/SKILL.md` にあります（このファイルを入口として要約したもの）。
**正本はこの WORKFLOW.md** です。ルールを変えたら、スキルも同じ PR で更新してください。

スキルを使えない環境では、次の文面をそのまま渡してください。

```
このリポジトリで作業するときは、最初に docs/WORKFLOW.md と docs/HANDOVER.md を読み、
その手順に従うこと。特に:

- push 前に npm run typecheck / npm test / npm run build を実行する

```
